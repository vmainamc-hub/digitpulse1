# Liquidity Pulse

Build and deploy this application as a production-ready Deriv Liquidity Intelligence platform.

Treat the supplied codebase as the complete analytical foundation. Do not simplify, replace, remove, or redesign the quantitative engines. Preserve the architecture and implement all existing engines as functional live components.

Connect the application to Deriv's public WebSocket market-data API and maintain the 15-market universe defined in the project. Use live ticks and historical bootstrap data.

The core purpose is to detect and explain observable statistical/psychological liquidity formation, not generic financial order-book liquidity and not DBot T1/T2/T3 logic.

Preserve and expose:

digit psychology

parity and LOW/HIGH psychology

boundary analysis

entropy/information theory

Markov/transition analysis

run/hazard analysis

regime/change-point detection

anomaly/fluctuation analysis

OVER/UNDER contract projections

liquidity formation → building → mature → absorbing → exhausting → ripe → release → confirmed lifecycle

liquidity sweep detection

contract-specific danger

structural-adversarial observable patterns

multi-dimensional confirmation

research/observation logging

Critical rules:

NO LIQUIDITY WITHOUT OBSERVED CREATION.

RIPE does not mean CONFIRMED.

A single indicator must never qualify a contract.

Conflicting evidence must remain CONFLICTED rather than being forced into a direction.

Do not claim actual trader manipulation or hidden order flow from tick data.

Keep the UI read-only with analysis separated from rendering.

Do not introduce DBot T1/T2/T3 logic into this application.

Make the UI professional, fast, responsive, and suitable for continuous live monitoring. Do not replace the analytical core with mock data or superficial dashboard scores.

After implementation, verify that the live data stream, market state, analytical engines, contract matrix, liquidity lifecycle, danger engine, and research journal all operate together correctly.
